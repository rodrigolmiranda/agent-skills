# Discovery, knowledge and re-baselining

Use only the mode needed for the authorized request; an approved continuation does not restart discovery or repeat approval.

## Authority and intake

Load applicable repository routing and adopted governance. Search existing owning sources before creating a note. Shared governance remains central; adopted product meaning belongs in product repositories, GitHub owns live delivery state, and artifacts own proof. Preserve unique source statements until reconciled. A missing secondary vault is not automatically a blocker when the actual owning authority is available.

For an insight, meeting or research input: identify its source and affected product, capability, actor and concepts; find the owning specification; incorporate only new or clarifying information; link evidence and unresolved questions; assess UX, architecture, security, delivery, tests, operational and downstream documentation effects. Update authority, audience, confidentiality and supersession metadata where used. Client-specific priorities belong in the project's accepted context, not universal skill defaults.

## Plan and grill

The coordinator resolves ambiguity and owns decisions. Establish current versus desired behavior, actors, workflows, rules, permissions, failure paths, non-goals and measurable outcomes. Check data/API/event ownership and operational effects against existing architecture and adopted governance; do not invent another stack default here. Challenge unsupported assumptions and unnecessary infrastructure. Prefer configuration when it soundly resolves a foreseeable variation without disproportionate complexity.

For a new milestone needing approval, return a concise pack: outcome, scope, workflows or mockups, rules, decisions and trade-offs, dependencies, risk and operating cost, non-goals, open questions and canonical links. Approval already recorded remains effective; ask the owner only about new material decisions outside it. Preserve future product intent while elaborating only the useful delivery horizon.

## Executable breakdown

Use the adopted governance's milestone/slice/task definitions. A checklist task does not become a sub-issue merely because an agent can execute it. GitHub mutations require authorization covering the repository, Project, milestone and issue scope; otherwise prepare a reviewable proposal. Existing authorization persists across routine checkpoints. Each independently accepted slice carries actor/outcome, current and desired behavior, canonical links, scope/non-goals, rules/permissions/errors/edge cases, UX where applicable, repository and migration dependencies, observable acceptance, proportionate validation, and documentation impact. Keep known context in the packet so workers need not rediscover the product. Select semantic roles and authorized model profiles here; Interchange resolves the supported execution route. Never silently substitute a model.

## Acceptance and knowledge closure

Obtain independent evidence against the accepted scope and current head. Require material-risk review for security, tenancy, money, migrations, data integrity, concurrency, infrastructure, recovery and cross-repository contracts. One qualified independent reviewer may cover that review alongside acceptance; a separate redundant review is unnecessary. Allocate browser/UX/full journey checks according to the plan and changed behavior, not a blanket repeat of every test. Reviewers report findings without repairing their own work. Route bounded corrections to the implementation owner, then re-review changed evidence. GitHub state follows proof, not process exit.

After acceptance, reconcile affected capability, architecture, decision, workflow and operational notes. Record stable code symbols, screens, APIs/events/jobs, data ownership, configuration, tests and observability without copying source. Link specification, issue, PR, evidence and residual limits. Update manuals/runbooks/training/UAT/release/RAG outputs only when affected; remove competing claims only after preserving unique information.

## Existing-system re-baseline

Inventory the relevant knowledge, code, GitHub, tests, deployments and observed behavior. Build a capability matrix classified as verified, partial, missing, obsolete, undocumented or conflicting. Verify material user-visible and high-risk claims against actual runtime where required. Record existing capability as baseline verification, not fabricated historical implementation. Create meaningful gap slices and keep knowledge/code/test/runtime links and residual risk together.

## Human report

Lead with outcome and approval state, any real decision needed, material evidence limits, and next action/owner. Keep detailed artifacts linked. Use governed measures rather than fabricated percentages. Planning completion is not implementation or runtime acceptance.
