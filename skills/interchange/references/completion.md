# Completion and monitoring contract

Each prompt carries its own packet ID and attempt ID, expected duration, review deadline (2x) and hard deadline (3x). IDs must be generated by the coordinator, not reused from another run. The prompt tells the worker when to stop and escalate, including repeated failure with no new evidence, unresolved requirements, ownership conflict and missing prerequisites.

Final assistant response is exactly one JSON object followed by the final marker on a separate line. No Markdown fence or prose follows the marker:

```text
{"packet_id":"packet-123","attempt_id":"attempt-456","result":"ready_for_review","summary":"Implemented assigned change; targeted checks passed.","evidence":["commit and test-log references"]}
INTERCHANGE_DONE:packet-123:attempt-456
```

`result` may be `ready_for_review`, `blocked` or `partial`. Additional handback details may be JSON fields. Evidence must identify actual artifacts, checks and unmet requirements. The marker means the attempt has returned a final report, not that the product is accepted.

Adapter first extracts the final assistant response from provider events. Never search raw stdout for a marker: it may appear in thinking, an echoed prompt or a tool result. Then `scripts/protocol.py` validates IDs, JSON schema, final marker and process result. Nonzero exit fails; missing process exit is still running; missing/mismatched marker is incomplete. Require nonempty evidence and reject duplicate JSON keys. This helper never returns accepted. A separate trusted verifier must bind acceptance to packet, attempt, repository and immutable reviewed head; a Boolean verification flag is insufficient.

Use `max(60, min(300, expected_seconds / 2))` seconds until the first fallback retrieval, then grow intervals by 1.5x within 60–300 seconds. Never sleep past a review/hard deadline. Completion and blocker events need no scheduled delay. These are retrieval intervals, not repeated inference calls. For tiny jobs, prefer direct tools or the process-completion event. Event readers can continuously consume stdout without model tokens.

At 2x expected duration ask once: 'Return progress evidence, current blocker, attempted approaches, remaining work and revised estimate. Stop and escalate if outside your assignment or capability.' A diagnostic response does not terminate the assignment or reset its clock. At 3x, interrupt and verify termination. An extension requires a recorded lead decision before expiry, with evidence and a new finite deadline. Do not postpone a hard limit while waiting for a diagnostic reply.

Adapt estimates using comparable successful deliveries and recent elapsed-time distributions once there is enough evidence; do not infer progress from text volume. Broad changes to limits or routing require weekly owner-approved proposals. A live token ceiling is available only where the adapter exposes timely counters; otherwise wall-clock and repeated-failure limits are the backstop.

Current implementation: pure protocol validation and scheduling helper, tested with synthetic inputs. Pending: provider final-event extraction, process supervision, cancellation/child tracking, durable event delivery and live cross-house recovery. Do not advertise these pending parts as active protection.
