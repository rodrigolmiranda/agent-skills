# Declared post-return publication

`run_job.py` accepts an **opt-in** `post_return` version 1 implementation contract. It is transport, not acceptance authority. The coordinator supplies the accepted packet revision, owned branch and paths, required gates, exact base/repository, current project generation, and independent reviewer route before worker launch. An ordinary manifest without `post_return` keeps the prior behavior. The runner never commits, merges, deploys, or declares acceptance.

## Execution boundary

The default `same_user` mode needs no privileged service or second account. It uses the installed OpenCode headless adapter with `run --pure --format json` and a runner-generated permission map. Shell commands are denied by default; the coordinator declares literal `allowed_bash` commands for implementation and gates. Git entries must begin with a permitted subcommand; global options and wildcard allow patterns are rejected. Direct `git push`, `gh`, browser/Chrome/Playwright/computer, web search/fetch, external-directory and task tools remain denied. The runner owns `OPENCODE_CONFIG_CONTENT`, so a manifest or inherited config cannot replace that map. Before launch it invokes the selected OpenCode executable's `debug config --pure`, verifies every declared permission, and refuses inherited MCP servers or plugins. `--pure` disables external plugins; the separate resolved-config check handles MCP rather than assuming `--pure` does. The pipeline currently starts a fresh session because reused sessions have not been qualified for permission-map persistence. These are mechanical tool restrictions for cooperative workers, **not a security boundary against a hostile same-user process**: the worker process can still read same-account credentials or run code through an allowed tool. The supervisor alone performs publication stages, and exact-head, owned-path, clean-tree and gate checks limit mistaken publication. Independent review, CI and human merge authority remain required.

`distinct_uid` remains an optional stronger host mode. A privileged supervisor launches the worker and reviewer under separate unprivileged UIDs with private homes. The worker account must have provider login but no GitHub publication credentials. The runner scrubs coordinator credential/browser environment variables, rejects known GitHub/Git/SSH credential paths in the worker home and checks `gh auth token` under the worker UID. The relay state and attempt roots must be supervisor-owned and mode `0700`, outside the worker checkout/home, with no worker-writable ancestor. State paths are canonicalized before opening or child handoff. These checks require actual host provisioning and do not prove isolation against arbitrary secrets embedded in provider configuration.

Use an owned worktree whose Git control metadata is trusted at launch. The runner records its control digest and refuses publication if `.git`, `config` or `config.worktree` changes. It rejects dangerous local Git config keys, suppresses hooks, fsmonitor, external diff and local credential helpers in publication Git commands, and pushes the exact validated SHA. Each commit in the worker range is checked for paths; merge commits require supervised integration. The declared GitHub URL and `repository` must match; a trusted absolute `gh_executable` is required. HTTPS uses that `gh` executable as the supervisor's Git credential helper. SSH uses the supervisor's batch SSH route. In `distinct_uid` mode the worker's dry-run push must fail with a recognizable permission/authentication error. A transient network error, non-fast-forward, or fake pre-push hook is not proof of denial.

The non-root fixture proves the full local worker return → draft PR → supervised headless reviewer transition with fake provider/GitHub adapters and a bare Git remote. It does not prove real provider-account access, GitHub permission mapping, browser integration state, or hosted CI overlap. Qualify the exact model/effort and routes with a supervised smoke before declaring unattended use. Do not silently substitute another model.

## Contract and run

Start from [post-return-manifest.json](../templates/post-return-manifest.json). Replace every placeholder and bind the worker attempt to the registered project/generation before launch (`relay.py register-project`, `register`, `bind-attempt`). The worker must begin at `start_head` on `branch` with a clean checkout. It writes a compact JSON final to `final_artifact_source` under the worktree; ignore that attempt-specific path in the common Git exclude. The runner copies and hashes it into the private attempt root. A ready final has exact `job`, `attempt`, `packet_revision`, and committed `head`, `result: "ready_for_review"`, and `required_gates` mapping each declared gate to `"passed"`. A known required-gate failure, question, dirty checkout, absent commit, out-of-scope commit, changed Git control metadata or changed head becomes a durable `post-return.json` exception. Existing Markdown finals remain valid for ordinary jobs but cannot authorize this pipeline.

Run `run_job.py --manifest <manifest> --state <private-state.db> --directory <attempt-root>` under a supervised background service. The parent process receipt and callback remain immutable evidence. `post-return.json` records `new`, `pushed`, `pr_created`, `review_started`, or `exception`, including the exact head and PR/reviewer references. The pipeline queries the remote and existing open draft PR before each stage. A retry never reruns the worker. For a failed or interrupted publication stage, inspect the lease/process/remote state and then run:

```text
python3 skills/interchange/scripts/post_return.py --manifest <manifest> --state <private-state.db> --directory <attempt-root>
```

This command updates only the post-return journal. It leaves the hashed process result intact. A lost or uncertain external operation requires inspection before retry; an existing managed-action lease must not be cleared merely because its inspection deadline passed. The monitor exposes exceptions and missing later stages. The coordinator handles corrections, verdict disposition, CI state and all merge/acceptance decisions.

## Reviewer adapter

The reviewer argv is literal and supplied in the manifest. The default same-user route is Claude headless with `--safe-mode --restricted --strict-mcp-config --mcp-config '{"mcpServers":{}}' --tools Bash,Read,Glob,Grep --no-chrome`, explicit browser/Chrome/Playwright/computer/MCP tool denies, and `--output-format stream-json`. These installed CLI controls ignore inherited user/project settings and MCP servers and disable installed customizations, including plugins; the runner rejects overrides, resumed sessions and a nonempty MCP config. The Bash tool remains useful for source review, so this cooperative same-user route is not hostile-process or prompt-injection isolation. Codex `exec --sandbox read-only --json` is available only with `distinct_uid` until its same-user owner-browser integration deny can be verified. Include explicit model and effort flags only after verifying account support. `{head}` and `{pr_url}` in argv are replaced at launch. Require the reviewer to return one JSON object as its final response with `reviewed_head` equal to the PR head and `verdict` equal to `passed` or `changes_needed`; the runner extracts it from the structured event stream. The startup stage requires actual assistant/tool activity or a valid immediate terminal verdict. PID, empty init, stderr or queue receipt alone are insufficient. The journal records requested model/effort and leaves observed values unknown unless independently verified. Review may start while hosted CI runs, but CI and review remain separate acceptance gates.

## Native completion recovery

Native subagents use the same durable activity ledger without fabricating a `run_job` process result. Before dispatch, the coordinator registers and binds the attempt, then declares its next authorized action with `relay.py --state STATE declare-next-action --contract CONTRACT.json`. The contract contains `action_id`, `project`, current `generation`, `source_job`, `source_attempt`, `source_kind: "native-completed"`, trusted literal `recovery_argv`, `cwd`, `deadline_at` and a qualified `recovery_route`. Never obtain executable arguments from a worker return.

The completion adapter records the real final artifact:

```text
python3 relay.py --state STATE emit --job JOB --attempt ATTEMPT --sender SENDER --kind native-completed --artifact FINAL --event-id EVENT
python3 monitor.py --state STATE --project PROJECT --recover
```

The second command must run through an independently scheduled heartbeat or supervisor, not only within the coordinator turn. It atomically claims the declared continuation before launching its adapter. The adapter receives `INTERCHANGE_ACTION_ID`, `INTERCHANGE_PROJECT`, `INTERCHANGE_OWNERSHIP_GENERATION`, `INTERCHANGE_SOURCE_EVENT_ID`, `INTERCHANGE_CLAIM_TOKEN` and `INTERCHANGE_RELAY_STATE`. After actual coordinator wake, it records `relay.py --state STATE recovery-awake`; after verified reviewer startup it records `relay.py --state STATE action-started --evidence-path PATH --evidence-sha256 SHA256`. Identity and claim arguments default from those environment variables. Inspect `relay.py --state STATE next-action --action-id ID`: `acceptance_met` requires the next action to have started within both the configured deadline and maximum latency. Launching the adapter or recording a queued event is insufficient.

The action-start proof file names `kind: "reviewer_started"`, the action ID, ownership generation, and exact `reviewer_job` and `reviewer_attempt`. The reviewer attempt must be registered, project-bound to that generation and launched after coordinator wake. Its supervised stdout must contain structured assistant/tool activity, or its terminal receipt and final verdict must prove a validated review of the declared head. A live PID, a launch row, and unstructured output such as `sleeping` cannot mark the action started. Supply `expected_head` in the declared action when a commit head is part of the review contract.

After takeover, an unclaimed action remains at its old generation until the new owner explicitly adopts it. Write a fresh qualified route proof for the current coordinator and generation, then call `relay.py --state STATE adopt-next-action --contract ADOPTION.json`. That contract contains `action_id`, `expected_generation`, `generation`, and `recovery_route`. Adoption preserves the original action ID, source completion, deadline and latency allowance, records the previous generation in `next_action_history`, and lets the scheduled monitor claim the action once. If the accepted work is explicitly withdrawn, use `dispose-next-action --contract DISPOSITION.json` with the same fields plus a concrete `reason`; this records a stopped disposition and cannot claim completion. A claimed, delivered or awake action cannot be adopted or disposed until its process and side effects are reconciled. Old-generation actors remain fenced.

The recovery route identifies an independently scheduled host route, current coordinator and generation, qualification/expiry times, maximum latency and a hashed local proof file. Its idle qualification must show ordered worker completion, queue, delivery, coordinator wake and actual next-action startup. `validate_recovery_route` in `relay.py` is the shared validator used by the scheduling gate. An expired or absent proof cannot justify unattended yielding. There is no generic promise that a local script can wake every client: qualify the installed host adapter separately.

The regression runs worker completion in a separate process while the coordinator is absent, races two scheduled monitor processes, and verifies exactly one reviewer launch. This proves ledger and adapter mechanics, not live Codex/Claude wake availability. An ambiguous interrupted claim remains for supervised reconciliation rather than blind relaunch.
